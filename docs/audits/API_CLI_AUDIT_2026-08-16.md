# SciRust API / CLI audit — 2026-08-16

Audit base: `master` at `4dbc92811a67471bcc07fa7e23cd1887d75934fb`.

This is a live, evidence-based audit note. It records only findings verified in the repository; hypotheses are kept out until reproduced or traced to source.

## Confirmed strengths

- Workspace inventory: 154 Cargo packages / 154 workspace members at the audited revision.
- The scanned production surface contains no active `todo!()` or `unimplemented!()` implementation slots.
- CI has an exact MSRV gate: Rust 1.89.0 runs `cargo +1.89.0 check --workspace --all-targets --locked`.
- CI separately exercises stable, pinned nightly, aarch64 cross-checks, WGPU/lavapipe, CUDA no-runtime fallback, cargo-deny, Miri, fuzz smoke tests, SBOM generation, and deterministic rayon-vs-serial fingerprints.
- `scirust-core/src/error.rs` explicitly defines the migration rule that new public APIs return `Result<T, SciRustError>` while assertions/panics may remain internal when they do not cross a public boundary.

## P1 — public lazy API turns expected input errors into panics

Files:
- `scirust-core/src/lazy/mod.rs`
- `scirust-core/src/lazy/plan.rs`
- `scirust-core/src/error.rs`

Verified behavior:

1. `LazyGraph::eval(&self, id) -> Tensor` panics when the reachable graph contains `LazyOp::Feed`.
2. `LazyTensor::value()` delegates to `LazyGraph::eval`, so a public tensor created with `LazyTensor::feed()` can panic through `value()`.
3. `Plan::execute_with()` panics when a required feed is absent.
4. `Plan::execute_with()` uses `assert_eq!` when a supplied feed has the wrong shape.
5. `Plan::execute()` delegates to `execute_with(&[])`; its current documentation says it executes with "feeds par défaut", but no dynamic feed values are supplied.
6. Existing tests cover valid dynamic-feed execution but not missing-feed or wrong-shape behavior.

This conflicts with the crate's documented public-error policy. Missing inputs and shape mismatches are ordinary caller errors, not compiler invariants.

### Recommended compatible correction

Do not break existing signatures immediately. Add fallible public methods first:

- `Plan::try_execute() -> crate::error::Result<Tensor>`
- `Plan::try_execute_with(...) -> crate::error::Result<Tensor>`
- then consider `LazyGraph::try_eval`, `LazyTensor::try_value`, and `LazyTensor::try_scalar`.

Keep the historical infallible methods as compatibility wrappers for one deprecation cycle, with accurate `# Panics` rustdoc. Reuse `SciRustError::ShapeMismatch` for feed-shape errors. A dedicated missing-feed variant is preferable if the error taxonomy is extended; otherwise `InvalidConfig` is an acceptable compatibility-first bridge.

Internal buffer `expect(...)` calls generated by the compiler are not classified as bugs by this audit unless a public input can reach them.

## P1/P2 — polynomial factorization has an undocumented failure panic

File: `scirust-modalg/src/poly.rs`.

`Poly::factor()` documents a panic for the zero polynomial. Its private equal-degree Cantor–Zassenhaus step additionally stops after `1000 * (n + 1)` attempts and then panics with `equal-degree splitting failed to converge`.

The public contract therefore does not completely describe the implementation's failure modes.

Recommended next step: either expose a fallible factorization path, remove/prove the artificial backstop, or document the additional panic with a regression/property test covering the chosen contract.

## P2 — incomplete panic documentation for `ExtField::build`

File: `scirust-modalg/src/extfield.rs`.

`ExtField::build(p, k)` can panic when:

- `k == 0`;
- `p` is not prime (validated indirectly by `Poly::from_coeffs`);
- `p^k` overflows `u128` in `checked_pow(...).expect("field too large to search")`.

The modulus validation itself is present, so this is not classified as a missing-validation bug. The gap is the public rustdoc contract.

## P2 — unified CLI mixes executable commands and non-dispatchable library crates

File: `scirust-cli/src/lib.rs`; reference: `docs/REFERENCE.md` §2.14.

`scirust help` includes 14 library-crate names in the same grouped help surface as executable commands:

- pattern detection: `scirust-vision`, `scirust-audio`, `scirust-graph`, `scirust-sequential`, `scirust-multivariate`, `scirust-unsupervised`, `scirust-seasonal`, `scirust-nlp-advanced`;
- algorithm creation: `scirust-automl`, `scirust-synthesis`, `scirust-algogen`, `scirust-codetrans`, `scirust-rl-algo`, `scirust-scaffold`.

The dispatcher intentionally does not implement them, and `docs/REFERENCE.md` explicitly says they are library capabilities, not subcommands. The implementation is therefore intentional, but the interactive help is ambiguous because it opens with `scirust <command> [args]` and renders these entries like commands.

Recommended correction: render them in a clearly labelled `LIBRARY CRATES (NOT SUBCOMMANDS)` capability section, separate from command groups. Add a test that preserves the distinction so future help changes cannot accidentally imply dispatchability.

## P2 — explicitly orphan/experimental public `scirust-core` modules

`scirust-core/src/lib.rs` documents the following public modules as having zero workspace consumers outside their own tests (workspace audit noted there as 2026-07):

- `lazy`;
- `amp`;
- `dp`;
- `pruning`;
- `logging`.

The source also states that `amp` overlaps `autodiff::mixed_precision` and should converge with it.

Recommended governance action: give each module one explicit disposition (`promote`, `merge`, `incubate`, `deprecate/remove`) and an owner/evidence gate. The existing documentation already supplies the facts needed to start that decision.

## Items intentionally not classified as bugs

- `scirust-frame` panics identified by the initial grep are under `#[cfg(test)]`.
- Private `lazy::plan` fusion panics are currently treated as compiler invariants; diamond cases have dedicated correctness tests. They should only be reclassified if a reachable public graph reproduces them.
- `pollard_rho`'s terminal `unreachable!` is private and follows a documented composite/odd precondition; non-termination/performance is a separate question.
- `ExtField::build` does validate `p` through `Poly::from_coeffs`; an earlier suspicion of missing prime validation was disproved by source tracing.
